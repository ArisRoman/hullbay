## 3. Campagne production (S1 à S10)

Instance live `http://ops.example.com` (v1.3.0-beta.2 via l'update in-app), compte admin dédié `campaign.owner@hullbay.test` (owner, seed TOTP contrôlé) — le compte owner réel `arisroman@mail.com` n'a jamais été sollicité.

| S8 | Sessions + RBAC | RBAC owner/operator/viewer, list/revoke sessions | **PARTIEL → 1 bug** |
| S9 | WebAuthn | routes register/auth/credentials | **NON-EXÉCUTÉ** *(env `WEBAUTHN_*` absents)* |
| S10 | Sécurité | rate-limit, anti-énumération, audit (271 events) | **PASS** |

**Résultats avant correction : 6 PASS / 2 FAIL / 1 PARTIEL / 1 NON-EXÉCUTÉ.** Les 4 bugs sont détaillés en section 4 et corrigés.

Notes de campagne :
- OIDC/OAuth2/SAML validés en **Keycloak test-mode** : des fournisseurs OAuth2/OIDC réels exigent des redirects HTTPS (impossible en http ; le callback est ici `http://ops.example.com/api/auth/sso/*`). Les flux réels par utilisateurs de l'IdP (login KC, code, state, userinfo) restaient authentiques.
- WebAuthn : `WEBAUTHN_ORIGIN`/`WEBAUTHN_RP_ID` non configuraient dans le container → réponse propre `webauthn_not_configured` (codée HTTP 500, fail-closed) ; la fonctionnalité elle-même est couverte par les tests unit A4 et l'e2e réel de la campagne auth précédente (A-E2E-R01/R05). Depuis, la recette de configuration est passée au code : `.env.template` + `docker-compose.yml` + `docker-compose.prod.yml` exposent `WEBAUTHN_ORIGIN`/`WEBAUTHN_RP_ID`/`WEBAUTHN_RP_NAME`, et `install.sh` génère les valeurs d'office sur une install HTTPS (`PUBLIC_HOST`). Il ne manque plus que le redéploiement api.

## 4. Bugs discovered and fixed

| # | Bug | Sévérité | Fichier(s) | Fix |
|---|-----|----------|------------|-----|
| 1 | OAuth2 : provider créé sans `clientSecret` persistant (champ optionnel au schéma) → échange code→token voué à l'échec (`invalid_client_credentials`), provider silencieusement inutilisable | Majeur | routes/providers.routes.ts | `clientSecret` **requis** à la création pour kind `oauth2` (400 explicite sinon) — le PUT fusionné conservait déjà le secret |
| 2 | Approbation d'une identité OAuth2 impossible : gate `issuer` null refuse tout provider hors `ldap`, or OAuth2 émet volontairement `issuer: null` → le flux se branche mais reste bloqué en `pending`, aucun compte rattachable | Majeur | identity/pending-approval.service.ts | Gate élargie : `issuer` null autorisé pour kind `oauth2` (au même titre que `ldap`) — le subject reste la clé de stabilité |
| 3 | LDAP en clair (`ldap://`) inutilisable : `createClient` injecte toujours `tlsOptions` → ldapts force le TLS (`hasTlsOptions`) même sur `ldap://` → `ECONNRESET` sur 389. Aucun annuaire en clair ne répond (forumsys comme osixia local) | Majeur | providers/ldap/ldap-provider.ts | `tlsOptions` passé uniquement si `rejectUnauthorized`/`ca` explicitement configurés ; `ldaps://` reste sécurisé (TLS dérivé du schéma) |
| 4 | Session courante jamais identifiable : `SessionHandle` (retour de `verifySession`) sans `jti` → `req.user.jti` undefined → `current:true` jamais posé ET « révoquer tous les autres appareils » révoque la session actuelle elle-même | Mineur | sessions/user-session.store.ts, routes/guard.ts | `jti` exposé dans le `SessionHandle` (fast-path cache-miss, payloads legacy tolérés) → marquage `current` correct et exclusion `notJti` effective |

**Outcome :** 4 bugs identifiés, 4 corrigés, 7 tests de régression ajoutés, 744/744 au vert.

## 6. Conclusion

**Fonctionnalité Auth largement saine en conditions de production** : tenancy (9/9), OIDC, SAML, LDAP (local), MFA TOTP, RBAC et sécurité (rate-limit réel 429 à la 6e tentative, anti-énumération, audit 271 events) sont au vert. **3 bugs majeurs** verrouillaient néanmoins deux connexions à des tiers : fournisseurs **OAuth2** (secret non requis à la création + approbation bloquée) et annuaires **LDAP en clair** (TLS forcé par ldapts), plus un bug mineur sur l'identification de la session courante. Les 4 bugs sont corrigés et couverts par 7 tests de régression ; la suite complète passe à **744/744**, typecheck au vert, **0 test préexistant modifié**. Le point de configuration WebAuthn (`WEBAUTHN_ORIGIN`/`RP_ID`) est désormais couvert au code (`.env.template`, composés dev/prod, `install.sh`) ; seule la revalidation live reste planifiée après redéploiement, avec le nettoyage de la VM.
